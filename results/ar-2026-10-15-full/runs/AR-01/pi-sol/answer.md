## Bounded refactor plan

**Choose a small lifecycle seam in `src/pr/`, not a universal PR effect coordinator.** Draft, ready, and merge all persist an exact intent before a possible external write, reconcile uncertain outcomes by reading, and must never redispatch an intent that might already have reached the provider. A shared helper can own the *admission result* (`record` plus whether this caller inserted it) and the rule that a retained or non-winning intent takes a read-only path. Keep observation predicates, dispatch, and error mapping in the three coordinators.

| Seam | Benefit | Limit |
| --- | --- | --- |
| **Coordinator lifecycle helper (preferred)** | Removes repeated winner/retry and uncertainty control flow without hiding the different write gates. | Keep it narrow; callbacks must not be allowed to authorize a write on a retained intent. |
| **Generic store or effect state machine** | Could consolidate `admit`, `markUnknown`, and `confirm` across all three tables. | Too broad for this pass: draft and merge begin `pending`, while ready has a retryable `preflight` and a compare-and-set transition immediately before dispatch. Confirmation data and identity keys also differ. A shared schema would add migration risk without resolving provider rules. |

**Keep authority and provider policy effect-specific.** Draft admission remains tied to confirmed hosting publication, frozen PR-only CI policy, and the pinned PR binding; its Gitea path searches by repository and branch pair and confirms an exact draft/head. Ready still requires the trusted policy milestone, exact preflight identity, and the durable `preflight → pending` winner before its private title update. Merge still requires the current Human decision and candidate; `requestExactMerge` retains its checks, approvals, fast-forward-only strategy, and exact merged-head confirmation. Neither the helper nor a provider adapter should infer those authorities. An absent or stale read after possible dispatch is **not** permission to write again.

**Migration in small slices:**
1. Add focused tests for admission outcomes and crash/retry boundaries before extraction. Have each store return an explicit *inserted versus retained* result from its atomic admission; do not infer ownership by comparing generated effect IDs. Preserve the three tables, unique keys, record shapes, and persisted state meanings.
2. Move draft’s and merge’s retained-intent/read-only decision into the narrow helper, one coordinator at a time. Integrate ready only where that decision applies; leave its `markDispatching` compare-and-set and preflight checks local.
3. Run the focused contracts after each slice, then reconcile `docs/authoritative/pull-request-adapter.md` only if the verified durable contract changes. This is a refactor, so **ablation: not required**—it proposes no experimental workflow behavior.

**Regression tests to add or retain:** name cases for a lost create response followed by exact-PR discovery; draft absence or lookup failure after a retained intent; concurrent draft and merge admissions **including identical injected effect IDs**; ready preflight read failure remaining retryable; concurrent ready compare-and-set with exactly one PATCH; lost ready response followed by confirmation or `unknown`; merge timeout followed by an unreadable, still-open, or wrong-head observation and later exact merged-head confirmation. Reopen the same SQLite database between calls in recovery cases and count provider POST/PATCH calls: at most one per admitted intent. Preserve conflict tests for changed binding, base, head, authority, or decision, and Gitea/provider-contract tests for exact identity and merge authorization.

**Rollback:** keep the existing tables and public coordinator interfaces during extraction. If a slice fails its focused checks, revert that helper’s use in the affected coordinator without rewriting durable records; do not reset `unknown` effects or issue compensating provider writes. If a future schema consolidation is considered, require a separate migration and recovery plan.
