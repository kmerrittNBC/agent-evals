**For the same admitted candidate, the coordinator does not issue a second provider merge after a timeout.** It records an intent first, and a later call with that candidate takes a read-only reconciliation path rather than calling `mergeFastForward` again (`src/pr/mergeCoordinator.ts:32–51`). That is a guarantee about this coordinator’s dispatch decisions, not proof that the provider performed exactly one merge.

- **Durable record and states.** The SQLite `pr_merge_effect` row pins the binding and revision, repository and PR identity, head SHA, base ref and revision, Human decision and actor, and effect ID. Its states are `pending` on admission, `unknown` when the outcome cannot be established, and `confirmed` after a matching observation. A uniqueness constraint covers `(binding_id, native_pr_id, head_revision)` (`src/pr/mergeStore.ts:28–75`; `src/storage/migrations.ts:3029–3047`). The coordinator requires a caller-supplied `verifyAuthority` check before admission; this module does not itself prove the Human decision is current.

- **Dispatch and confirmation.** On first admission, `requestExactMerge` reads the PR and checks its exact head and base, open/non-draft status, fast-forward strategy, mergeability, required checks, and current attributed Human approvals. It then asks the adapter for a fast-forward merge of the exact head. Even if that call throws, it reads again. Success requires a provider observation for the expected repository/PR reporting `merged`, with both the PR head and `mergedRevision` equal to the approved head SHA (`src/pr/contract.ts:63–113`; `src/pr/mergeCoordinator.ts:50–62`). The Gitea request supplies `head_commit_id`, disables force and queued merge, and leaves the branch intact (`src/pr/gitea.ts:172–178`). A timeout followed by an open, absent, or unreadable observation is **unknown**, not failure or success.

- **Retry and competing admission.** An existing row makes a retry read the PR only: a matching merged observation confirms it; otherwise the coordinator reports `merge_outcome_unknown` without dispatch. Admission with the same candidate key but different pinned authority or base data throws `pr_merge_identity_conflict`. If another admission wins between the coordinator’s lookup and insert, the returned effect ID differs from its proposed ID, so this caller likewise reconciles by read rather than dispatching (`src/pr/mergeStore.ts:28–44`; `src/pr/mergeCoordinator.ts:34–49`). This protection is scoped to that candidate key and retained SQLite record; it is not a claim about arbitrary other candidates or provider-side behavior.

- **What is established.** In-memory SQLite tests show `pending` exists before the mock provider write; a mock timeout leaves `unknown`; retries make no additional mock merge call; a subsequently mocked matching merged read confirms. A second test injects a competing admission and observes zero merge calls from the losing coordinator. Store tests cover idempotent admission, conflicts, and revision-mismatched confirmation. Contract and Gitea tests cover denial checks and the request payload (`src/pr/mergeCoordinator.test.ts`, `src/pr/mergeStore.test.ts`, `src/pr/contract.test.ts`, `src/pr/gitea.test.ts`). They do **not** establish actual concurrent-process behavior, provider atomicity, or what a real timeout means at Gitea. The repository search shows the coordinator instantiated in tests, not wired to a production merge caller; `src/storage/store.ts` constructs the store, but the caller’s authority verification and end-to-end task completion are not proved by these tests.
